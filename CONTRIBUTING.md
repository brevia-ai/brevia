# Contributing to Brevia

These rules apply to people and to coding agents alike. Agents also follow [AGENTS.md](AGENTS.md), which covers authorisations and reporting. Every change, including one generated by an agent, must be understandable and verifiable by a human maintainer: its flow, dependencies and effects must be recognisable.

## Setup

Requirements: [uv](https://docs.astral.sh/uv/) and Git. uv installs the Python versions the project needs.

```sh
uv sync --locked
cp .env.example .env   # local settings and credentials, ignored by Git
```

Brevia needs PostgreSQL. The development database is in `compose.yaml` (start it with `docker compose up -d --wait`, then `uv run brevia db upgrade`); unit tests do not need it.

The development environment comes from `uv.lock`. Do not upgrade dependencies or Python as a side effect of another change.

## Workflow

1. **Stage and plan.** Work is organised in stages, listed in [docs/IMPLEMENTATION.md](docs/IMPLEMENTATION.md). Before writing code for a stage, write a plan: the sections of the specification it implements, files and interfaces, tests, verification criteria and open questions. The maintainer approves it.
2. **Branch.** Create a branch from `1.x`, the branch of Brevia 1.0, named after the kind of change, for example `feat/configuration` or `fix/job-retry`.
3. **Implement** with the rules below, and keep the change focused on one purpose.
4. **Check** locally: formatting, lint, types and unit tests (see [Checks](#checks)).
5. **Update the records:** an entry in `docs/implementation-log.md` with the change and its evidence; `docs/IMPLEMENTATION.md` when the status, a deviation, a known limit or a planned item changes; `CHANGELOG.md` for changes visible to users of the library; the documentation site for any public feature (see [Documentation](#documentation)).
6. **Pull request** with the template. Review follows the [review procedure](.github/skills/code-review/SKILL.md). Merges into `1.x` are squash merges.

## Checks

| Check | Command | When |
|---|---|---|
| Formatting | `uv run ruff format --check` | always |
| Lint | `uv run ruff check` | always |
| Types | `uv run mypy` | always |
| Unit tests | `uv run pytest` | always |
| Integration tests | `uv run pytest -m integration` | on request; needs `BREVIA_TEST_DATABASE_URL`, for example the database of `compose.yaml`; each test uses its own temporary schema |
| Tests with real models | `uv run --env-file .env pytest -m ai` | on request; calls a provider and incurs costs; the key comes from the local `.env` |
| Quality corpus | `BREVIA_CORPUS_REPORT=corpus.json uv run --env-file .env pytest -m ai tests/ai/test_corpus.py -s` | on request, before a release or after a change of prompts, analysis or model adapter; about twenty OpenAI calls; prints the measures of each case and writes them as JSON |
| Documentation site | `uv run --group docs zensical build --strict` | always, when `docs/` or public docstrings change |

The continuous integration workflow runs formatting, lint, types and unit tests on Python 3.12, 3.13 and 3.14, the migrations and integration tests on a PostgreSQL service, builds the documentation site in strict mode, and builds the package and installs it in a separate environment, checking that migrations and prompts are included. A pull request is merged only when it passes.

## Database migrations

Migrations live in `src/brevia/db/migrations/` and are applied with `brevia db upgrade`; they create objects only in the configured schema and never assume `public`.

Until the first release there is a single initial migration, edited in place at each stage: no installed database needs to be preserved yet, and the schema follows the contracts as they settle. After the first release every change is a new incremental migration, with a working downgrade. When the initial migration changes, recreate the development schema (see the database guide).

## Style and typing

| Area | Rule |
|---|---|
| Formatting | Ruff formatter, 4 spaces, 88-character target. URLs and strings that cannot be split may exceed it. |
| Lint | The Ruff rule sets selected in `pyproject.toml`, each with a reason. Do not enable rules wholesale. |
| Types | mypy in strict mode on `src/` and `tests/`. Annotate every public function, class and attribute; the package ships its types (`py.typed`). |
| Names | English identifiers; `snake_case` for functions, variables and modules, `PascalCase` for classes. Names describe the task; avoid generic containers that collect unrelated responsibilities. |
| Documentation | Docstrings for public behaviour, raised errors, external effects and constraints. Comments explain reasons that the code cannot show; they do not paraphrase it. |
| Suppressions | Lint or type suppressions are local and justified in a comment. No global disabling, and no `Any` used to hide an incompatibility. |

Annotations do not replace runtime validation: data that enters from outside is validated at the boundary.

## Size and complexity

These are signals for review, not automatic errors or universal standards. Lines are physical lines, including comments and docstrings.

| Element | Guideline |
|---|---|
| Module | Preferably within 300–400 lines; beyond 500, re-examine its responsibilities and justify keeping it together. |
| Function | Preferably within 40–50 lines, with one recognisable task. |
| Nesting | Beyond 3 levels, consider early returns or a meaningful extraction. |
| Parameters | Beyond 5–6, consider whether a coherent concept deserves a typed object. |

Do not split readable code just to meet a number. Declarative tables, migrations, fixtures and parametrised cases may justify exceptions. Avoid refactoring outside the purpose of the change.

## Structure

The organisation of the package, the flow of runs and jobs, and the invariants a change must keep are described in [docs/architecture.md](docs/architecture.md).

- Prefer functions for recognisable operations and flows that read from top to bottom. Use classes for resources and coherent behaviours; avoid deep hierarchies and automatisms that hide the flow.
- Use Pydantic at the boundaries: external input, configuration and structured output to validate. Use dataclasses for simple internal data when useful, and dictionaries for genuinely variable mappings. Avoid redundant conversions between equivalent representations.
- Pass dependencies explicitly. Introduce a small `Protocol` when it isolates a concrete variation, such as model providers or storage. Do not add layers, hierarchies or generalisations for hypothetical needs.
- Organise modules by feature: core, adapters and functional modules stay distinct. The HTTP API is a thin layer over the same Python operations.
- Keep computation and transformation separate from effects on the database, the file system and model providers, so that they can be used and tested without the durable execution engine.
- No mutable global state and no input or output at import time.
- Prefer explicit loops and conditions to compact expressions that are hard to read. Use `async` for supported waits, without imposing it on ordinary computation.

## Reliability

- Errors are explicit: no swallowed exceptions, no empty values presented as success, no silent fallbacks. Preserve the cause and the useful context without exposing secrets.
- Control timeouts, cancellation, concurrency and the lifecycle of resources. Do not block the event loop with CPU-bound or blocking work.
- Respect the guarantees of durable execution: no concurrent paths that bypass checkpoints. A job interrupted with its worker runs its activity again from the beginning, so external effects must bear a repetition.
- Make idempotency, file ownership, publication of results and the consequences of retry and of a new start after an interruption explicit.

## Logging

- Use the standard `logging` module with one logger per module (`logging.getLogger(__name__)`). The library emits events; the application configures levels, destinations and format. The library never configures logging at import time.
- Readable format in development, structured JSON in production, console as the initial destination. Collection and retention belong to the runtime environment.
- Propagate request, run and activity identifiers, including into jobs. Record start, completion, duration, retry, timeout, cancellation and failure; for model calls, the provider, the model and the available usage.
- Levels have a uniform meaning: `DEBUG` for diagnosis, `INFO` for significant events, `WARNING` for recoverable problems, `ERROR` for failed operations. Record the cause and the stack trace once, where the error is handled.
- Never log credentials, tokens, document contents or full prompts and responses, including inside error messages from dependencies.
- Operational logs and AI traces are distinct and linked by the run identifier. Sensitive details go only into traces, whose access and retention are controlled.
- OpenTelemetry integration is planned. Before adding instrumentation, check what Pydantic AI and DBOS already provide, to avoid instrumenting twice.

## Tests

- Tests carry a marker: `unit` for deterministic tests without external services, `integration` for tests that need a real database or local services, `ai` for tests that call a real model provider. Unknown markers are errors.
- Write a test when it protects a behaviour or a concrete risk. Do not write tests that duplicate the implementation, and do not require a new test for every documentation change or low-impact reversible change.
- Read the assertions: they must be able to detect the regression they are meant to prevent, including errors, limits and significant edge cases.
- For variable model output, use meaningful criteria and thresholds on versioned datasets, not indiscriminate textual identity. Record models, prompts, configurations and conditions so that comparisons can be interpreted.
- A simulated model proves the behaviour of the code, not the quality of a real model.
- Unit tests use the store in memory (`tests/unit/memory_store.py`). The behaviour every store must have is in `tests/store_contract.py`, run on that store by the unit tests and on PostgreSQL by the integration tests: a change of the database store adds its case there, so that the store in memory cannot drift from it.
- Wait for events, not for fixed times: a test that sleeps before a cancellation or an assertion fails at random on a slow machine. Use `asyncio.Event`, the job gate of `test_jobs.py` or the end of a later job, always with a timeout (`asyncio.wait_for(event.wait(), 5)`), so that a regression fails the test instead of leaving it hanging.

## Documentation

The documentation site is built with [Zensical](https://zensical.org/) from the Markdown pages in `docs/`, with the Python API reference generated from docstrings by [mkdocstrings](https://mkdocstrings.github.io/). Configuration is in `zensical.toml`.

- Every public feature is documented when it is added: Google-style docstrings for the API reference, and a page or section of the guides with its behaviour, errors and limits.
- Keep available and planned features clearly separate. Do not document planned behaviour as available.
- Examples must match the real API. Prefer short, complete examples over fragments that cannot run.
- The site is built in strict mode: broken links and missing references fail the build. Preview locally with `uv run --group docs zensical serve`.
- The HTTP API is documented separately, with the OpenAPI schema generated by FastAPI.

## Project template

The [project template](docs/guides/project-template.md) is in `copier.yml` (questions)
and `template/` (files, with Jinja placeholders); it is not part of the wheel and the
library's Ruff excludes it. A change of the public API that the template uses changes
the template in the same pull request. The default of `brevia_source` in `copier.yml` is
the version of Brevia on PyPI that generated projects install: the pull request of a
release changes it together with the version in `pyproject.toml`. Check a change by
generating a project from the working tree, with Brevia from the local checkout, and
running its checks:

```sh
rm -rf /tmp/brevia-gen
uvx copier copy --trust --defaults --vcs-ref HEAD -d brevia_source="file://$PWD" . /tmp/brevia-gen
cd /tmp/brevia-gen && uv sync && uv run ruff format --check . && uv run ruff check . && uv run pytest
```

`--vcs-ref HEAD` takes the working tree, uncommitted changes included: without it Copier
takes the latest stable tag of the repository, a release of Brevia 0.15 without the
template.

Without a database the tests that run the activity are skipped; with the database of
`compose.yaml` and `uv run brevia db upgrade` they run too.

## Changes and compatibility

- Describe the behaviour before and after, the reason, the checks actually run and the known limits.
- Declare incompatible changes to the public API, configuration, snapshots, stored data or jobs started with a previous version, with their effect on callers and existing data. Do not assume conversions or compatibility.
- Dependency updates go in their own pull request, with the reason and the relevant release notes.
