# Implementation status

This file records where the implementation stands: the stages, what each section of the specification has, the deviations, the known limits and the planned items. It is updated by every change that alters one of them. Each change, with the evidence collected for it, is recorded in the [implementation log](implementation-log.md). This file does not restate the specification: it refers to its sections.

**Specification:** [`PROGETTO-BREVIA-1.0.md`](spec/PROGETTO-BREVIA-1.0.md), written in Italian. Section numbers below (§) refer to it.

**Status values:** *planned* (not started), *in progress* (partially implemented, on a branch or merged), *done* (implemented and verified as stated), *deferred* (outside the first release, §5).

**Evidence types:** *static* (formatting, lint, types), *unit* (deterministic, simulated models), *integration* (real database or services), *model* (real provider), *human* (manual review).

## Stages

The first release (§5) is built in stages. Each stage starts from an approved plan and ends with a merged pull request. After stage 4 the library covers what a consumer demonstrator uses: the demonstrator is moved from an interface prototype to this library and its checks are repeated, before the remaining stages. Direct runs were moved from stage 3 to stage 1, so that the core can be verified end to end without a database.

## Deviations from the specification

| Section | Deviation | Reason and follow-up |
|---|---|---|
| §7.3 | Token counters not reported by a provider are recorded as zero, not `null`, also in `model_calls`. | Pydantic AI's `RunUsage` uses zero for counters a provider does not report, so the adapter cannot tell them apart. To be revisited if provider-level information becomes available. |
| §8.3 | `runs` has no `parent_run_id` or external context; the DBOS workflow of a job has the identifier of the run instead of a column of its own. | External context with the integrations that need it, by editing the initial migration until the first release; `parent_run_id` with agents. |
| §8.3 | `model_calls` has one row per logical call with its number of attempts, not one per attempt, and no prompt revision; each provider request of the call, retries included, is a `request_records` entry of the row (with the response and request identifiers for OpenAI and Anthropic), not a row of its own. `trace_contents` has one row per logical call too, without the messages of intermediate attempts. | The usage of a call is reported and limited as a whole; the prompt version of a run is in its snapshot. |
| §7.8 | For a failed call the invalid output of the model is not captured, only the error code; NUL characters are replaced by U+FFFD in every record. | The adapter returns no output for a failed call; PostgreSQL refuses NUL in text and JSON. To revisit with the evaluation module if the invalid answers are needed. |
| §7.5 | Cancelling a running job stops it within about a second, also in the middle of a model call; the calls made until then are recorded with the job. A call stopped before the model answered may miss its last request. | The run of a job is a preemptible DBOS step, which DBOS stops when it sees the cancellation (it checks every second). |
| §7.8 | The recorded steps of a job (DBOS checkpoints) keep input, configuration and prompts, also with `capture="metadata"`, until `retention_days` after the job ended. | Deleted by the daily cleanup; a rule for every copy of the data is still due before production (audit item). |
| §7.3 | Prompt templates have no optional variables and no escape for a literal `{name}`. | Not needed by the current consumers; to be added with a declared syntax when a project needs it. |
| §7.6, §8.3 | No upload, no `files` or `run_files` tables, no fingerprinted archive of documents: inputs are downloaded from the URLs of an allowed host (or copied from a local path by trusted code) into a work folder removed at the end of the run, and outputs are files of the run, referred to by run and name. The criteria on interruptions during a publication are met by the design: an output is written apart and moved into place, under a name that a job started again replaces. | Decided with the maintainer in the plan of stage 4: the current consumer keeps its documents in its own system and passes URLs. Upload, archive and storage adapters when a project needs them, without changing activities. |
| §7.5, §8.3 | Tools are passed per generation with `generate(tools=...)`; no `run_agent`, global registry or separate `tool_calls` table. Offered names and counts are stored with model calls; logs contain name, outcome and duration, not arguments or results. | Approved stage 6 plan: reuse the model loop and run budgets; effects must tolerate retries. |
| §7.4 | No registry of model adapters that a project extends: the adapter is chosen by the provider of the model reference (`openai`, `anthropic`, `ollama`), through Pydantic AI. | Deferred (review of 19 October 2026): no consumer needs another provider yet; the interfaces of Brevia (`ModelSpec`, `ModelClient`, usage records) do not expose Pydantic AI, so a registry can be added without changing activities. |
| §7.5, §9.1, §11.6 | The routers are not mounted one by one: `create_app(brevia)` returns one FastAPI app with every endpoint of Brevia, and the application adds its own to it. | Decided with the maintainer in the plan of stage 5, against `add_routers(app)` of Brevia 0.15: start and stop, caller and errors cannot be forgotten. An `install` on an existing app can be added when a project needs it. |
| §8.3, §9.2 | No events or progress of runs: no `run_events` table, no `GET /runs/{id}/events` or `/usage`, no streaming. A job is followed with `GET /runs/{id}`; usage is in its state. | Left out of stage 5 in its plan; the usage of a direct run is in the log and in `runs`, not in its answer (next items). |
| §9.2 | `POST /runs` has no contract version, no external context and no callback; `GET /activities/{name}` has no configuration schema; the lists of activities, configurations and prompts have no cursor. | Not needed by the current consumers; the activity version is in the state of a job, the configuration schema in `GET /configurations/{activity}`; the lists are short. |
| §9.3 | Prompts are addressed as `/prompts/{activity}/{name}`; no `POST /prompts/{key}/render`, no `GET /models`, no `GET /usage`; no Postman collection. | A prompt belongs to an activity; preview, models, usage and the collection were left out of stage 5 in its plan. |
| §9.5 | The calls and traces of a run are not readable over HTTP or from Python. | Recorded in `model_calls` and `trace_contents`; a read operation is among the next items. |
| §8.3 | `feedback` has `source` and `idempotency_key`, not in the specification. | Added after the comparison with similar tools agreed with the maintainer (17 October 2026). |
| §11.3 | The request identifier of the HTTP API is in every answer and in the log record of a failed request, not in the records of the runs and jobs the request starts. | The run identifier links the records of a run; the error of a failed direct run carries it. To propagate when a project needs to follow a request across its runs. |
| §7.9 | The status token is `BREVIA_STATUS_TOKEN`, not `STATUS_TOKEN`. | Every setting of Brevia has the `BREVIA_` prefix; the rule of `/status` is that of Brevia 0.15. |
| §11.5 | The reference image is in the project template, not in the library: the `Dockerfile` and `bin/start` of a generated project run its worker and API, together or apart, and its `compose.yaml` runs the image with the profile `app`; the `compose.yaml` of this repository has the database only. | Brevia 1.0 is a library with no application to start: each project builds the image of its own application. The image runs as root for now, so that it can write to volumes mounted as root. |
| §7.5 | A call whose response goes over the tokens left counts its tokens but not its request, so `max_requests` and the recorded usage may understate by one request. | Pydantic AI 2.55 counts a request only when it accepts the response, and its error does not tell a limit reached before the request from one reached after it. Owning the provider clients (3b) does not change it: it is how Pydantic AI reports the limit; to revisit with a later version of the adapter. |

## Deferred optimisations and checks

- **`psycopg[binary]` is a dependency of the library.** psycopg recommends that libraries leave the choice of the binary or C implementation to applications. Kept for simplicity of installation; its licence is compatible with the MIT licence of Brevia (P9).
- **Prompts replaced by a single request** (as the `prompts` payload of Brevia 0.15) are not supported. Possible extension, decided with the maintainer to wait for a need: opt-in per activity, with the variables of the file checked and source `request` in the snapshot.
- **No test compares the table definitions with the migrated schema.** `db/tables.py` and the initial migration are kept in step by hand. To be checked by an integration test with Alembic's `compare_metadata` after `upgrade head`, in a separate pull request.
- **Unused activity tables of the project file are not reported.** A typo in `[activities."<name>"]` leaves the table unused without warning. To be added as a start-up check once all activities are registered.
- **Lists of jobs reconcile every active job first.** Before a page, `JobService.list` (`jobs/service.py`) reads in batches the full records of all the active jobs the query may show and asks DBOS for their statuses: twenty results do not bound the work to twenty records. Fine with few active jobs; before production, read only identifiers and statuses, or reconcile only the jobs of the page (review of 19 October 2026).
- **Waiting for a job reads its whole record.** `RunHandle.result(wait=...)` reads the full row of the job every 250 ms, with input, snapshot and result, and asks DBOS for its status. Not part of stage 5, since the HTTP API does not wait for jobs (decision of 17 October 2026): when needed, read only status and error while waiting and the full record once at the end, keeping the reconciliation with DBOS (review of 16 October 2026).

## Next items (agreed with the maintainer, 17 October 2026)

After stage 7 and the release of the current consumer on a minimal Brevia 1.0, decided with the maintainer on 17 October 2026: none of them is needed by that consumer. It is distributed as a pre-release on PyPI (decision of 19 October 2026).

- **Reading feedback.** `Brevia.feedback(run_id)` and `GET /runs/{run_id}/feedback`, with the access policy of the run; possibly a list across runs filtered by activity, kind and date, for the evaluation module. Feedback is written today and read only with SQL.
- **Reading direct runs (usage, status, output).** The answer of a direct run has its identifier and output; its usage and model calls are only in the log and in the `runs` and `model_calls` tables. A read operation for runs, direct and jobs, would let a caller see them. Brevia 0.15 returned the usage in the answer (`usage` of `/completion`, `token_data` of `/chat`).
- **Input size from the context window of the model.** `summarize` and `extract` divide a document longer than `max_input_chars` (120,000 characters by default, about 30,000 tokens, suitable for every current model). The right size depends on the model: the project could declare the context window in `[models]`, and the size would follow from it, instead of a fixed number. Asked by the maintainer on 19 October 2026.
- **A `brevia run` command.** Decided on 16 October 2026 to come with stage 5, as the `test_service` command of Brevia 0.15, and not implemented: runs start from Python or over HTTP; with fake models a project already runs without a provider.
- **More feedback fields, when a project needs them.** Langfuse scores, LangSmith feedback, Braintrust and Phoenix annotations and the OpenTelemetry `gen_ai.evaluation.result` event share a name of what is judged, a numeric, boolean or categorical value, a comment, a correction, the source and an idempotency key. Brevia has the corrections, the rating `good`/`bad`, the comment, the source and the key; still missing: a name of the criterion, for a run judged on several aspects (correctness, tone); a numeric score; a link to one model call of the run instead of the whole run.

## Findings of the checkpoint (16 October 2026)

A consumer demonstrator that generates two documents was rebuilt as an application on the library: activities, project file, worker and caller, with the logic of the documents carried from the demonstrator and its tests. Its tests pass, and both documents were generated by a separate worker with the fake model and with a real one; only the data sections of the real output were compared with the demonstrator's reference draft, and they match. Using the library from outside gave these findings. None changes the library now; each needs its own plan when it is taken up.

- **Finding a job by its idempotency key only by submitting it again.** A caller that lost the identifier of a job sends the same request with the same key to get it back; the application keeps the identifier meanwhile. Done in stage 5: `Brevia.find_job` and `GET /runs?activity=…&idempotency_key=…`.
- **Settings shared between activities (future).** Two activities of one application may share part of their configuration. In the consumer the shared part described a common input file, and it was solved in the application as a schema default, which Brevia validates and records in the snapshot like the rest. A library feature only if several applications need it.
- **Checks of generated texts as a library tool (future).** The consumer checks that quotes are in the sources, that numbers are in the quotes, word limits and forbidden terms, and gives the model precise corrections. Other applications may need the same; candidate for an optional module.
- **Tests of an application without PostgreSQL (future).** Running an activity in tests needs the database, even with the fake model; without it the consumer's activity tests are skipped.
- **Cost unknown when a price is missing.** With a real OpenAI model the usage reported cache-write tokens and the project file declared no `cache_write` price, so the runs recorded their cost as unknown, as designed. The guide on models could say that prices should cover every kind of token the provider reports.
- **Prices from a catalogue when the project declares none (proposal, 19 October 2026).** Providers expose no pricing API (OpenAI lists only model names), so every project copies prices by hand and keeps them updated. Pydantic AI already installs `genai-prices`, a price catalogue maintained by Pydantic that Brevia does not use; the installed version has `gpt-6-luna` with cache writes and the tier above 272K input tokens, which the project file cannot express, and can optionally download an updated catalogue. Proposal: when a declared model has no `prices`, estimate the cost from the catalogue, and keep the project file to override it; to decide whether the catalogue version is pinned or updated at run time.
- **A recommended structure for applications.** Brevia 0.15 had a project template (`brevia-cookiecutter`). Brevia 1.0 has a Copier template in the repository (`copier.yml`, `template/`), not part of the wheel; Copier rather than Cookiecutter because `copier update` brings later changes of the template, such as the HTTP API of stage 5, into existing projects. A separate repository may follow.

## Audit of 14 October 2026: items for later stages

An external audit of the repository, the specification and the laboratory confirmed the direction and found defects fixed before stage 3 (see the log). The items below are accepted and belong to later stages; they are recorded in the specification too.

- **Stage 3, verification scenarios (done; the publication of a file met by the design of outputs in stage 4, see the verification table):** stop between recording a run and enqueueing it; stop after a provider response but before its checkpoint (a step may run more than once: the usage of the lost call is unknown, not zero); stop after publishing a file but before recording the outcome; response lost by the caller after an accepted submission; cancellation during a call or a publication; release with queued or interrupted jobs; usage rebuilt without duplicates on replay.
- **Stage 3, design (done; usage from the steps superseded, see below):** a job resolves its configuration and prompts in the worker, in its first DBOS step, from the recorded input, overrides and customisation; a resumption reads them from the checkpoint of that step and a `retry` resolves them again from the same recorded values. Overrides of jobs must therefore have a JSON form, as the input. This answers the audit point on snapshots that may not validate back to the same configuration (fields excluded from serialisation, custom serialisers) without rebuilding from the snapshot, which stays a record. A first attempt that recorded the inputs of the resolution in the snapshot (pull request #8) was closed: it broke direct runs with overrides without a JSON form and needed special cases for NUL characters, strict schemas and `Any` values. Retries of provider SDKs, Pydantic AI and DBOS coordinated with the run limits; usage recorded idempotently from the steps; a durable deadline instead of the time of the process; run execution moved from `application.py` to an internal module, with `Brevia` as the facade; queue concurrency of DBOS distinguished from limits on model requests; the results of a DBOS spike on 14 October 2026 (specification §7.5).
- **Stage 4 (done, simplified):** access checks on the operations that exist (status, result, cancellation, retry, outputs of a job, changes of customisations); lists, traces and feedback get the filter of the policy when they come with stage 5. The open mode without authentication only with `BREVIA_AUTH_DISABLED=true`. A consumer that freezes its external data: the library keeps the input of a job and checks the fingerprints of its files; reading the data before `submit` and passing it in the input is the part of the consumer, described in the files guide.
- **Before production:** a retention rule for every copy of the data (metrics, input, output and snapshot, DBOS checkpoints, files, approved datasets); a simulated run on the installed wheel in CI, and an update procedure for the adapters; limits between runs (concurrency per worker and per provider, queue overload, connections per process, memory, drain time) measured with a representative load; backup and restore.
- **Superseded on 15 October 2026:** with the new start from the beginning (see the deviations, §7.5), the stage 3 items above on the usage of a lost call, usage rebuilt on replay and idempotent usage from the steps no longer apply: the calls of a lost execution are not recorded, and the outcome of a job is written once.
- **First release:** a small versioned evaluation corpus (normal, ambiguous, incomplete and negative cases) with separate measures of schema validity, faithfulness, completeness, retries, cost and latency; three runnable examples in the documentation (deterministic activity, validated generation, job with files and a new start after an interruption), each stating what Brevia guarantees and what remains to the consumer.

## Stage 6: limits

Readers (PDF, DOCX, UTF-8 text), run file reading, pieces, `map_reduce` and `refine`,
`summarize` and `extract`, typed tools with paged reading and text saving, the template
registration and the guides with executable examples.

No OCR, PDF table reconstruction, XLSX/PPTX readers, parallel strategy calls, new HTTP
shortcuts, global tool registry or per-tool-call database table. Tool input and output
names come from the application, never paths chosen by the model. Model calls and tool
corrections share run limits; effects must be repeatable. A truncated read continues
within its section using `next_offset`; reader caches are run-scoped. The parsed text
of a document may still be large: response pagination is not a parser memory limit.
Every step of `extract` is validated against the schema given to it, so a field found
only in a later piece must be optional there; completeness is checked by the activity
after `extract` returns (guide *Analysis activities*). Verified with simulated models
only: the evaluation corpus and the real providers belong to stage 7.
